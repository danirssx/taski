# B0 · Baseline del producto

Decisiones del 12 de noviembre de 2026, vinculadas al [issue #2](https://github.com/danirssx/taski/issues/2). El mantenedor aceptó el prototipo v3 y autorizó completar e integrar B0. La [dirección visual](../design-direction.md) y el [PR #1](https://github.com/danirssx/taski/pull/1) conservan la evidencia previa sin duplicar el trabajo de diseño.

## Alcance y reglas

- Un proyecto por instalación: Worker, D1, configuración y acceso independientes. Núcleo reutilizable, sin datos reales del equipo en el repositorio.
- TypeScript para la futura aplicación. API y MCP usan los mismos casos de uso; la UI puede reemplazarse.
- Código compartido y selección de persona. No introducir OAuth ni jerarquías de permisos en v0.1.
- Tipos `task` y `feedback`; estados `todo`, `in_progress`, `in_review`, `done`; responsable opcional e IDs estables.
- Convertir feedback en tarea conserva ID, URL, conversación y auditoría. Resaltar es independiente del estado.
- Un PR principal manual por ticket; no inferir su estado en GitHub.
- UI aceptada: Inter, captura inline, lista mínima, detalle derecho no modal, resaltado y feedback móvil resumido. Temas por tokens y marca discreta.
- Worker + D1, sin Durable Objects ni sincronización por WebSockets en v0.1. R2 no se necesita para texto.

## Política de finalización de agentes

Predeterminado: `agentsCanComplete: false`. Un agente puede crear, asignar, comentar, trabajar y pasar a `in_review`. Una persona verifica el resultado y lo pasa a `done`. La regla pertenece al núcleo y se aplica igual desde web, HTTP y MCP, sin depender de botones ocultos.

Una instrucción humana explícita puede delegar la finalización de un encargo concreto. Registrar actor declarado, canal, alcance y referencia de autorización en la auditoría, sin copiar conversaciones privadas. Esa delegación no modifica el valor global. En el contrato experimental, una escritura de agente a `done` sin autorización falla con `REVIEW_REQUIRED` y no guarda cambios parciales. La representación y validación de esa autorización se implementan en B3/B4; el spike local no autentica personas.

La orden del mantenedor de completar y mergear B0 autoriza el cierre de los tres issues de este bloque una vez verificados e integrados. Los demás issues siguen el flujo habitual.

## Recorridos que debe conservar la implementación

1. Persona entra con código, elige identidad, crea una tarea inline y la comparte mediante URL estable.
2. Agente consulta, crea/asigna, lee detalle y comentarios, deja avance, enlaza PR y pasa a revisión.
3. Miembro desde móvil escribe feedback con título/descripción, conversa y conserva el enlace al convertirlo en tarea.
4. Dos clientes editan: una versión obsoleta produce conflicto sin sobrescribir; un reintento idempotente no duplica datos.
5. Otro desarrollador clona, configura otro proyecto y sustituye tema/UI usando la API sin editar reglas del dominio.

## Criterio de terminado por bloque

Todos los issues incluyen documentación acorde al comportamiento, validación registrada y un PR enfocado hacia `main` con cierre enlazado. Un bloque se completa al integrar sus issues y demostrar estos resultados:

| Bloque | Evidencia requerida |
| --- | --- |
| B0 | Baseline acordado, auditoría saneada y spike reproducible con presupuestos y protocolo de benchmark. |
| B1 | Base TypeScript/CI y Worker+D1 locales; un colaborador reproduce el onboarding. |
| B2 | Configuración validada y tokens/componentes del diseño aceptado, sin acoplar marca al núcleo. |
| B3 | Tickets, conversión, conversación, auditoría atómica, versiones y reintentos probados. |
| B4 | Código y selección de persona para web/MCP; misma política de acceso/finalización en el núcleo. |
| B5 | API versionada y cliente sin React; ejemplos de errores, paginación y operaciones equivalentes. |
| B6 | Ocho herramientas; operaciones compuestas; versiones/cursor; defaults compactos. Claude Code/Codex verificados y benchmark frente a Linear optimizado. |
| B7 | Lista inline, detalle con ruta estable, conversación, resaltado, teclado, temas y responsive sobre API. |
| B8 | Feedback móvil y conversión probados con miembros no técnicos. |
| B9 | Enlace manual a PR visible y auditable, sin integración automática. |
| B10 | Segunda instalación independiente y cambio de UI reproducidos mediante guías públicas. |
| B11 | Despliegue Cloudflare, exportación/restauración y piloto comprobados. |
| B12 | Paquete open source, guías verificadas y compatibilidad de actualización documentada para v0.1. |
| Q2 | Adjuntos R2, SwiftUI y sticky notes con contratos y pruebas propios cuando comience esa fase. |

## Fuera de v0.1

Imágenes, audio, SwiftUI y sticky notes siguen en [Q2](../q2.md), una fase futura sin fecha calendario. Ninguna prueba de B0 presenta esas funciones, ni el backend o MCP de producción, como disponibles.
